# Kiro 企业账号自助管理平台（积分池版）· 产品文档

> Self-Service Kiro Account Provisioning with Feishu — Credit Pool Edition
>
> 面向使用 Kiro 企业版、并以**积分池**（credit pool，控制台名 Credit sharing）管理用户的客户：
> 把「建账号 → 加组 → 发密码邮件 → 加入积分池 → 设用量上限 → 台账登记」的多步控制台操作，
> 收敛为一条「员工自助申请 → 飞书审批 → 全自动开通」的流水线，并把积分池的余额、消耗与上限放到一个页面上管。
>
> 2026-11 之后新建 Kiro profile 的 AWS 账号只能用积分池；按人订阅的旧版本见 `release/subscription` 分支。

---

## 1. 积分池的规则（平台据此设计）

| 项 | 规则 |
|----|------|
| 席位 | $20 / 席位 / 月，每席位向池里贡献 500 credits / 月；首月按剩余天数折算 |
| 月度 credits | 先用；账期（UTC 自然月）结束过期，不结转 |
| 追加 credits | 一次性购买，12 个月有效；月度 credits 用完后按到期时间先后扣 |
| 计费方式 | 按 AWS 账号定。**后付**：加人即自动占座，按人计费；**预付**：先在控制台买席位，人多于席位时多出来的人「等待席位」 |
| 用量上限 | 个人 > 所在组里最高的组上限 > profile 默认（按人，不是池子总额）> 无上限；即时生效，到上限当月暂停；不能超过池子当前 credits 总量 |
| 超额 | 没有 overage：池子用完即停 |
| 购买 | 买席位 / 买追加 credits 只能在 Kiro 控制台 checkout 完成 |

## 2. 解决什么问题

| 痛点 | 现状 | 平台方案 |
|------|------|----------|
| 开通繁琐 | 管理员在控制台手工建 IDC 用户 → 加组 → 发密码邮件 → 加入积分池 → 设上限 | 审批通过后全自动执行，全步骤幂等 |
| 审批割裂 | 员工在 IM 里喊话，管理员开电脑进控制台 | 飞书卡片审批，手机上点「通过」即完成开通 |
| 池子是黑盒 | 剩多少、每天烧多快、什么时候用完，要在控制台几个页面之间来回看 | 「积分池」页一屏看全：剩余 credits、日均消耗、预计耗尽日、席位、配额 |
| 额度分配难 | 谁能用多少，只能在控制台逐个设 | 员工自助申请调整上限走审批；管理员可直接设个人 / profile 默认上限 |
| 台账缺失 | 谁有账号、谁在用，靠 Excel | DynamoDB 映射为唯一真相源 + 积分池实况实时对齐 |
| 多开浪费席位 | 一人多个账号，每个都占席位 | 每人一个账号，申请 / 审批 / 绑定三处校验 |
| 存量混乱 | 平台上线前手工建的账号游离在外 | 一键扫描游离账号，智能建议归属，绑定即纳管 |

## 3. 用户视角

### 员工（自助）

1. 飞书扫码登录 Web 门户（OAuth，无需另设密码）
2. 「申请账号」：系统按姓名拼音推荐可用用户名，选分组；可选填每月 credits 上限和理由
   - 提交即校验：用户名占用（平台台账 + IDC 实查）、邮箱唯一、每人一个账号、没有处理中的申请
3. 审批通过后查收密码设置邮件，登录 Kiro 开始使用；飞书会收到结果通知
4. 「我的 Kiro 账号」：积分池状态（已开通 / 等待席位 / 已停用）、本月上限及来源、本月已用；需要更多额度时「申请调整上限」

### 管理员（治理）

飞书收到审批卡片，**手机上直接批**；或进 Web 管理后台：

| 页签 | 能力 |
|-----|------|
| 申请审批 | 待审批列表，通过 / 拒绝（与飞书卡片同源防重）；「全部」视图同时是操作审计 |
| 积分池 | 余额、月度 / 追加 credits、日均消耗与预计耗尽日、席位、profile 默认上限、配额、购买记录 |
| 账号总览 | 指标卡 + 图表 + 账号列表（一行一人），设上限 / 停用 / 恢复 / 分配席位 / 用量回溯 / 批量停用回收 |
| 分组管理 | 直接新建 IAM Identity Center Group，申请表单下拉实时生效 |
| 存量导入 | 扫描 IDC 游离账号 → 邮箱 / 拼音双级归属建议 → 确认绑定纳管 |

## 4. 核心功能清单

### 4.1 自助申请与审批开通

- 审批双入口：飞书交互卡片（WS 长连接收回调，免公网）/ Web 后台，同一状态机防重
- 卡片附积分池现状一句话：剩余 credits、已占座人数；后付池提示「通过后自动占座，每人 $20/月」，预付池提示空余席位
- 回调立即响应（飞书要求约 3 秒），读库、防重、开通、更新卡片全部在后台执行
- 开通步骤：IDC 建用户 → 加组 → 密码设置邮件 → 加入积分池 → 席位（后付自动占座；预付调 AssignSeats）→ 可选个人上限；分步错误定位
- 预付池没有空余席位时开通仍算成功（用户已在池里，状态「等待席位」），结果卡片带提示；管理员在控制台买席位后点「分配席位」
- 每人一个账号：已有账号或已有处理中的申请时拒绝提交；两条申请同时被通过时，第二条在开通前失败，不留孤儿 IDC 用户

### 4.2 积分池总览

- 计费方式（预付 / 后付）、本账期起止与剩余天数
- 池内剩余 credits / 总量；本月月度 credits 已用进度；追加 credits 剩余与本账期到期量
- 日均消耗与预计耗尽日（含「月度 credits 用完、开始消耗追加 credits」的时间点）；顶栏常驻剩余量，预计账期内耗尽时红色提示
- 席位：已占座、等待席位、本账期计费席位、整月席位费；预付池另显示已购 / 空余 / 待删除
- profile 默认上限查看、修改、删除；可接入用户上限（附 Service Quotas 提额链接）；每月最多可买 credits
- 追加 credits 购买记录（时间、数量、来源、有效期、剩余）；买席位 / 买 credits 给出控制台操作路径

### 4.3 用量上限

- 员工「申请调整上限」→ 审批 → 即时生效；卡片显示当前上限与申请上限
- 管理员直接设个人上限（可高于或低于组上限，0 = 禁用）或 profile 默认上限；删除即回落到下一级
- 前置校验：上限不能超过池子当前 credits 总量（月度 + 追加），超了直接给可读提示
- 每次设置 / 删除都落审计记录（谁、何时、从多少到多少）

### 4.4 账号台账与积分池实况

- DynamoDB 映射表为唯一真相源：以 IDC UserId 为锚点（不随改名漂移）
- 积分池实况：每次展示都读 AWS（席位列表 + 成员列表），控制台里直接移出 / 改上限也能反映；拉取失败降级显示快照
- 每个账号：积分池状态、本月上限及来源（个人 / 组 / profile 默认 / 无上限）、本月已用 / 上限（80% 橙色、到顶红色）、本月消息、最后活跃
- 指标卡：账号数、积分池内、等待席位、本月 credits（全员）、本月有用量的人、用到 80% 上限的人数

### 4.5 停用 / 恢复 / 回收

- **停用** = 立即移出积分池：马上失去 Kiro 访问；已用 credits 不退，本账期席位费照收，下个账期起不再计费
- **恢复** = 重新加入积分池（预付池同时分配席位，席位不足时成功但提示等待席位）
- **回收** = 移出池 + 清个人上限 + 删除 IDC 用户 + 解除映射，不可恢复；之后此人可重新申请
- 批量：列表按分组 / 积分池状态 / 上限来源 / 本月用量 / 未活跃天数筛选，预设「长期不用的账号」；弹窗只做「核对 + 确认」，名单 ≥ 10 须手输账号数，名单与结果可导出 CSV，超过 200 个自动分批；逐账号落审计

### 4.6 用量看板（User Activity Report）

- Kiro 每天 02:00 UTC 把前一天的按人活动写到客户账号的 S3；平台用 Athena 分区投影表查询（不需要 Glue crawler）
- 按人本月 credits、消息数、活跃天数、最后活跃；按 UTC 自然月回溯
- 积分池用户的报表 `Subscription_Tier = POOLING`，`Usage_Limit` 为个人上限（999999 = 无个人上限）

### 4.7 存量导入 / 分组管理

- 一键扫描 IDC 游离账号，邮箱精确匹配（高可信）▶ 用户名拼音匹配（需人工核对）；已有账号的飞书用户不可选
- 分组即 IAM Identity Center Group，管理端新建后申请表单下拉实时生效

## 5. 安全基线

| 项 | 做法 |
|----|------|
| 凭证 | 全程 IAM Role（EC2 Instance Profile / ECS Task Role / EKS IRSA），代码层无任何 AK/SK 读取路径 |
| 权限 | 运行角色策略随仓库提供（`infra/iam-policy.json`） |
| 网络 | 飞书回调走 WS 长连接，**无需公网入站**；服务只监听 127.0.0.1，对外经 HTTPS 反向代理 / ALB，安全组限制来源 |
| 认证 | 飞书 OAuth（state 写入 HttpOnly cookie 并在回调校验，防登录 CSRF）+ JWT；JWT 密钥缺失或少于 32 字符即拒绝服务；登录 token 走 URL fragment，不进服务器日志 |
| 授权 | 管理员白名单（open_id 列表）；所有管理接口按管理员校验 |
| 静态文件 | 只返回前端构建目录内的文件，`..%2f` 之类的路径穿越被拦截 |
| 存储 | 报表与查询结果桶四项 Block Public Access 全开、默认加密、只允许 TLS；报表桶只允许 Kiro 服务以本账号身份写入 |
| 防重 | 审批状态机条件更新，多管理员并发点击只有一人生效 |
| 审计 | 申请 / 审批 / 执行 / 设上限 / 停用 / 回收 / 恢复 / 分配席位全量落 DynamoDB requests 表 |

## 6. 技术架构

```
员工 / 管理员
   │ 飞书 OAuth / 卡片审批（WS 长连接，免公网）
   ▼
FastAPI (Python 3.12) ── React + AntD (TS) 同源托管（只监听 127.0.0.1，经 HTTPS 反代对外）
   │
   ├─ IAM Identity Center          建用户 / 加组 / 组管理 / 存量扫描 / 密码邮件
   ├─ Kiro 积分池控制面             加入 / 移出积分池、分配席位、设置用量上限、购买记录
   │   management.{region}.kiro.dev（SigV4，服务名 q）
   ├─ Kiro 订阅服务（只读）          席位状态、池余额、生效上限
   │   service.user-subscriptions.{region}.amazonaws.com
   ├─ Service Quotas（只读）         可接入用户上限、每月可买 credits
   ├─ S3 + Athena                  User Activity Report 按人用量（分区投影表）
   └─ DynamoDB × 2                 账号映射（真相源）+ 申请 / 审计
```

- 所有外部依赖都做了**降级设计**：池余额 / 席位 / 上限 / 用量 / 配额任一不可用时，界面显示占位符并提示，核心开通链路不受影响
- 单 EC2 t3.small 即可承载数百人规模；无状态设计，可平迁 ECS / EKS

## 8. 边界与已知限制

如实说明，避免落地时才发现：

- **积分池管理接口没有公开 SDK**：平台按与控制台一致的服务接口手动签名调用，AWS 侧变更可能需要适配（已收敛在 `kiro_api.py` / `pool.py`）
- **买席位、买追加 credits、删除空闲席位只能在 Kiro 控制台完成**：checkout 需要支付方式与浏览器校验，平台只给操作路径
- **预付池流程尚未在真实预付账号上验证**：分配席位 / 等待席位 / 无席位时开通的逻辑按接口结构实现并有单元测试；后付池已在真实账号端到端验证
- **组级上限、把整个组加入积分池**：接口支持，这一版后台只做了个人上限与 profile 默认上限；在控制台把组加入积分池后，组内成员会自动获得访问，平台实况能显示但不会管理组级配置
- **停用不等于省当月的钱**：移出积分池立即生效，但本账期席位费照收、已用 credits 不退；预付池要少付席位费还需删除空闲席位
- **按人用量为日级**：报表每天 02:00 UTC 写入前一天数据，只包含当天用过 Kiro 的人
- **新账号可接入人数**：受 Service Quotas「Maximum allowed users to onboard per Kiro profile」约束，超出时开通会给出可读提示
- **存量导入的绑定目标**：仅覆盖在平台登录 / 申请过的飞书用户（平台默认不申请通讯录权限）
- 定位为 **sample code**（MIT-0），生产部署前请按贵司安全合规要求评审
